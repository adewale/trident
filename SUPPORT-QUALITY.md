# Quality of Trident support

Assessment: 2026-10-28. This ranks the depth and evidence of Trident integrations, not renderer speed, correctness or project quality. Ties avoid false precision. The eight-project retained campaign establishes that collection was attempted; it includes failures and gaps and predates portable protocol v4.

Order: inspected execution evidence first, then breadth of applicable public interfaces and reviewed observers. Among projects outside that campaign, configured portable calls precede existing transport labels and candidate declarations. Those lower tiers rank configuration confidence only. No new execution of the other 80 entities is implied.

Native model APIs add diagnostic depth where available. Their absence is not a failed renderer test, and the Mermaid-only original suite earns no support-rank bonus. SVG-centric harness coverage makes terminal and native/WASM tools less deeply supported today; that is a Trident limitation.

## Where to improve support

First verify Ondine. Skip the unbranded Beautiful-compatible descendants in normal comparisons. Then add broad terminal acceptance/meaning workloads and runtime-appropriate timing, so Mermaid ASCII is assessed on its real interface. Complete declared Dart PNG and Frankenmermaid terminal/diagnostic/source bindings before inventing more Node wrappers.

Invite each project to review its public invocation and supported-family contract. Keep those reviews separate from measured results. Give the same SVG to the same observer regardless of the project name. A richer model can provide extra evidence without lowering an otherwise valid SVG-only score.

Use `bun commands.ts support` for the current suite matrix and reasons; this dated assessment can age. [Lineage](LINEAGE.md) determines comparison candidates. [Benchmark methods](BENCHMARKS.md) and [report reading](REPORTING.md) define the scopes that must remain separate.
